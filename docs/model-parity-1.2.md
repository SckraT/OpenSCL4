# Матрица переноса моделей в OpenSCL4 1.2.x

[Матрица моделей](model-parity-1.2.json) включает все 40 публичных кодов из
[`DeviceModel`](../lib/src/devices/device_model.rs) на ревизии `7e90bb78`.
По каждому коду указаны действующий драйвер, парсер состояния, запросы при
подключении, модули настроек и идентификаторы, видимые в деморежиме.
[Задача #184](https://github.com/SckraT/OpenSCL4/issues/184) ·
[Методика волны #183](https://github.com/SckraT/OpenSCL4/issues/183)

Семейство указывает, какие чтения и кодеки можно переиспользовать. Для записи
определяющими остаются модули модели, формат тела команды и состояние, по
которому можно подтвердить результат. Один legacy-драйвер используют пары
A3027/A3030, A3028/A3029, A3931/A3935, A3933/A3939 и D1202/D1202C. В legacy
выбор драйвера начинается с кода зарегистрированного устройства. Распознавание
кода по входящему кадру проверяется отдельно.

## Как читать матрицу

- **Возможность.** Каждый ключ в `models[].modules` ведёт в `moduleOperations`
  к регистрации операции, источникам чтения и сборщикам записи в действующем
  драйвере. `model.stateParserSource` указывает на точный парсер из строки модели.
  `operationSources` задаёт отдельный запрос и парсер, когда модель получает
  данные операции через специальное чтение.
  `outboundRead` ссылается на `startupOperations`. Из перечисленных чтений
  применяются зарегистрированные в `startup` и `conditionalStartup` модели.
  `inboundUpdates` указывает обработчики, которые участвуют при их регистрации.
  Пустой `outboundWrite` соответствует чтению. `demoSettings` фиксирует 1 131 видимую запись
  из `list-settings --json --no-categories` в трёх группах — информация,
  элементы настройки и действия. Список содержит также клиентские операции
  с локальными профилями и зависит от демосостояния. Например, действия над
  существующим будильником D1301 появляются после чтения списка будильников.
  [Исходники D1301](../lib/src/devices/soundcore/d1301.rs)
- **Доступность.** `availability` указывает обработчик, который выставляет
  настройку по состоянию устройства. `operationVariants` уточняет формат,
  условия или недостающий эталон для указанных моделей. Например, при одном
  подключённом наушнике часть настроек недоступна, а LDAC доступен для чтения.
  Версию, наличие поля и текущую конфигурацию учитываем отдельно.
  [Правила клиента](../lib/src/client/availability.rs)
- **Результат.** Поле `evidence` описывает источник, `result` — результат
  отдельной проверки. `legacy` означает протокол действующего драйвера,
  `parityPending` оставляет проверку новой сессии открытой. `coreCoverage`
  фиксирует уже подтверждённые операции пилотов. `legacyFixture`
  означает эталон, выведенный из legacy-теста. `protocolFixture` означает
  синтетический кадр по известному формату. `captureReplay` означает
  воспроизведение аппаратного захвата. Ссылки `hardware` ведут на записанный
  физический прогон. `confirmedReadBack` отмечает подтверждение результата
  чтением для указанного сценария. В рабочей сессии `Applied` требует свежего
  совпадающего состояния текущего подключения. Для действий без читаемого
  состояния применяется согласованное подтверждение приёма.
  [Контракт сессии #137](https://github.com/SckraT/OpenSCL4/issues/137#issuecomment-7133425212)

Исходящие форматы сверяем с результатами исследования приложения Anker Soundcore,
когда есть совпадение по команде и модели. Корпус из 503 исходящих кадров
проверяет разметку кадров и контрольные суммы. Подтверждение конкретной
записи требует эталона запроса и соответствующих входящих ответов.
[Происхождение корпуса](../core/data/README.md#provenance)

## Первый сценарий A3028 и A3029

Обе модели используют [`A3028StateUpdatePacket`](../lib/src/devices/soundcore/a3028/packets/state_update_packet.rs).
[Эталонные кадры](../core/data/a3028-a3029-mode-reference.json) задают `01 01`
для чтения и `06 81` для цикла Normal → ANC Transport → Normal. Смена режима
сохраняет остальные три байта настроек. После каждой записи сценарий запрашивает
новый `01 01` и сверяет режим. В кадре состояния сохраняются версия 02.30 и
пример кривой EQ из legacy-теста. Вариант с ANC меняет байт режима и контрольную
сумму. Восстановленное состояние совпадает с начальным.

Исходный тест вызывает драйвер A3028, а в поле идентификации его единственного
примера состояния стоит префикс A3029. Для обоих публичных кодов эталон подставляет
синтетический серийный номер в байты тела 44–59 и пересчитывает контрольную
сумму. Эти два варианта проверяют общий формат на виртуальном транспорте.
Для обоих кодов сквозные тесты сверяют исходящие команды режима, восьмиполосного
EQ и автоотключения. Сессия подтверждает запись по заранее заданным ответам
состояния. Для автоотключения проверяются варианты с дополнительным блоком и
без него. Эталон блока составлен по legacy-формату.

## Сценарий dualWithPeers: C30i, AeroClip, V20i и C50i

Модели A3330 (C30i), A3388 (AeroClip), A3876 (V20i) и D1101 (C50i) перенесены
общим драйвером `dual_with_peers`: у них совпадают начало `01 01` с двумя
батареями, двумя прошивками и серийным номером, а дальше расходятся заряд
кейса, флаги, подсветка, баланс и команды записи. Эталонные тела состояния и
их происхождение описаны в
[`core/data/README.md`](../core/data/README.md#a3330-a3388-a3876-and-d1101-paired-state-references).
Идентификация подтверждена по `01 05` (две прошивки и серийный номер) и по
серийному номеру в состоянии, когда отдельный ответ идентификации недоступен.

В новой сессии подтверждены чтением обе батареи, заряд кейса у C30i и AeroClip,
обе прошивки, TWS-сторона, EQ, а также модельные флаги: touch tone и low battery
prompt у C30i/AeroClip; подсветка, баланс, voice prompt, автоотключение и
игровой режим у V20i; LDAC, кнопки и автоотключение у C50i. Записи EQ, игрового
режима, автоотключения, LDAC и кнопок сверяют исходящий кадр с legacy-сборщиком,
виртуальный транспорт применяет запись и отвечает новым состоянием, после чего
сессия подтверждает результат по свежему чтению. Для EQ проверены три формата:
общий с DRC для A3330, каналы с DRC для A3876, два одинаковых канала для A3388 и
D1101; команда D1101 — `02 81`, остальных — `02 83`. Жесты и их сброс, а также
список подключённых устройств остаются в legacy: в сессии пока нет команд
настройки кнопок и чтения пиров. Подсветка и баланс V20i только читаются.
У моделей разные таблицы автоотключения: A3876 — 10/20/30/60 минут, D1101 —
30/60/90/120 минут; тело записи общее, `[признак, индекс]`.
[Тесты сессии](../core/crates/session/tests/dual_with_peers.rs) ·
[Тесты моделей](../core/crates/models/tests/dual_with_peers.rs) ·
[Задача #191](https://github.com/SckraT/OpenSCL4/issues/191)
